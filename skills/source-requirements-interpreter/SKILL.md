# 源码需求解读

## 核心原则

- 将源码视为现有产品行为的事实材料，不将代码结构直接翻译成需求文档。
- 仅使用两类依据：用户指定范围内可确认的源码事实，以及用户明确给出的补充或修正。
- “需求溯源表”是独立的源码证据索引，其范围严于正文：只能收录源码事实，禁止收录、映射或为“用户补充说明”伪造源码依据。
- 允许用户补充或修正覆盖源码现状；覆盖后以用户最终确认的内容为准。
- 禁止自行补全业务规则、交互、文案、样式、异常处理或重新设计方案。
- 面向产品、设计、运营、业务人员及其他非程序员，使用产品与业务语言。
- 最终 Markdown 文档语言默认跟随用户使用的语言；用户明确指定语言时采用指定语言。
- 保持语言、框架、平台、仓库结构和 Agent 无关。

## 执行流程

### 0. 确认是否附加需求溯源表

开始读取和解读源码前，必须先询问用户是否在最终文档末尾附加“需求溯源表”。如果用户已在当前请求中明确选择附加或不附加，则直接采用该选择，不重复询问。

每轮只能提出一个问题。使用清晰、无默认倾向的问法：

> 是否在文档末尾附加“需求溯源表”，以需求编号映射源码相对路径和行号？

等待用户明确选择后再继续。禁止替用户决定、默认附加或默认省略。

用户选择附加时，在分析过程中保留可验证的源码相对路径和行号，仅用于文档末尾的溯源表；正文仍保持非技术化。用户选择不附加时，不在最终文档中输出源码路径、行号或代码映射。

### 1. 确认解读范围

要求用户明确指定以下任一种输入：

- 源码文件或目录；
- 代码片段；
- 提交、分支或版本差异；
- 用户明确圈定的其他代码范围。

未指定范围时，只询问源码范围。每轮只问一个问题，等待回答后再继续。

只读取用户指定范围。理解指定源码必须读取范围外的直接依赖时，先暂停并提出一个问题，说明：

- 需要读取的文件或范围；
- 当前源码缺少的必要信息；
- 不扩展范围会影响理解的具体需求点。

取得用户明确同意后才能扩读。禁止以“完善上下文”为由主动扫描无关源码。

### 2. 确认输出位置与功能名称

优先使用用户指定的输出位置。用户未指定时，将文档写入当前项目根目录的 `source-requirements/`。

默认文件名为 `<功能名称>-需求设计.md`。无法从源码或用户输入中确定唯一、清晰的功能名称时，只询问功能名称，不得使用“功能说明”“需求文档”等模糊名称代替。

目标文件已存在时，先询问如何处理，禁止直接覆盖。

### 3. 提取产品事实

按产品语义分析源码，只记录能够确认的内容：

- 功能目的与对用户产生的作用；
- 使用角色、适用场景与可见范围；
- 页面、模块、入口和信息层级；
- 用户动作、系统反馈与页面跳转；
- 业务条件、限制、优先级和状态变化；
- 表单字段、默认值、输入限制和提示文案；
- 加载、空、禁用、成功、失败及其他状态；
- 数据展示、排序、筛选、分页和关联关系；
- 权限、角色差异和可操作范围；
- 视觉样式、响应式表现、动画与交互状态。

将函数、变量、组件、接口、事件和数据结构转换为用户可理解的产品含义。最终文档不得讲解这些代码元素本身。

### 4. 提取视觉样式

从源码中可验证的样式声明、设计变量、组件属性、图形资源和布局规则提取视觉设计，包括：

- 宽度、高度、最小尺寸和最大尺寸；
- 内边距、外边距、元素间距和栅格关系；
- 字号、字重、行高、字间距和文字颜色；
- 背景、边框、圆角、阴影和透明度；
- 图片、图标及其他视觉元素的尺寸；
- 排列方向、对齐、定位、层级和滚动方式；
- 响应式断点及不同屏幕下的变化；
- 悬停、聚焦、按下、选中、禁用等状态样式；
- 动画、过渡、持续时间和触发条件。

仅在源码存在明确数值或可确定规则时写出精确描述，例如：“按钮宽度为 20px、高度为 10px”。

无法确认最终生效值、单位、条件或覆盖关系时，将其视为歧义并追问，禁止自行换算、选取或补充设计值。

### 5. 识别并逐个澄清歧义

将以下情况视为必须澄清的问题：

- 同一功能存在冲突行为或互斥规则；
- 条件、状态、角色、边界或异常路径不完整；
- 命名无法确定真实产品含义；
- 存在多个同样合理但产品结果不同的解释；
- 样式声明无法确定最终表现；
- 用户补充与源码事实冲突；
- 缺失信息会影响需求含义或文档准确性。

采用严格的单问题问询：

1. 每轮只提出一个独立问题。
2. 说明当前无法确定的需求点。
3. 说明已观察到的冲突、缺失或多种解释。
4. 说明不同答案会造成的产品差异。
5. 等待用户回答后检查一致性，再决定下一个问题。
6. 用户回答与既有事实冲突时直接指出冲突，要求用户确认采用源码现状还是用户修正。
7. 用户无法确认关键歧义时停止，不生成完整或部分的假设版本。

不得用默认值、行业惯例、常见设计或 Agent 经验代替用户决定。

### 6. 形成最终需求依据

澄清完成后，将结论整理为：

- 源码中能够确认且未被用户修正的需求；
- 用户明确补充或修正后的最终需求。

将用户补充或修正集中写入“用户补充说明”章节。该章节作为用户后续重新设计的起始点，无需标注其是否来自源码，但不得据此扩展、推演或生成任何未经用户确认的新设计。

用户修正与源码冲突时，不在最终需求中同时保留两个互斥版本；采用用户最终确认的版本。

用户选择在文档末尾附加“需求溯源表”时，为源码事实形成的正文需求分配稳定编号，例如 `REQ-001`；正文保持产品化、非技术化，不内联源码路径、行号、函数名、类名、变量名或其他代码标识。

需求溯源表至少包含以下列：

| 需求编号 | 需求摘要 | 源码相对路径 | 行号 |
| --- | --- | --- | --- |

每条记录只映射能够直接证明该需求的最小源码范围。一个需求存在多处源码依据时，使用相同需求编号分为多行记录。路径必须相对于当前项目根目录，行号使用明确的单行或起止范围。

仅映射最终仍以源码事实为依据的需求。用户补充或修正的内容保留在“用户补充说明”章节，不强行关联源码；用户修正覆盖源码现状时，禁止在溯源表中建立虚假映射。

### 7. 按需组织文档

根据实际依据选择章节，不强行填充源码未体现且用户未补充的内容。可使用以下结构：

```markdown
# <功能名称>需求设计

## 文档说明
## 产品目标与功能作用
## 使用角色与场景
## 功能范围
## 页面结构与信息层级
## 功能设计
## 业务规则
## 交互设计
## 页面与功能状态
## 表单与输入规则
## 数据展示规则
## 权限与可见性
## 页面跳转与功能关系
## 视觉与样式设计
## 用户补充说明
## 需求溯源表（仅在用户明确选择附加时生成）
```

只保留有事实内容的章节。使用清晰标题、列表、表格和短段落，避免技术术语。

### 8. 使用图形表达复杂关系

当纯文字难以准确表达时，在 Markdown 中使用 Mermaid：

- `flowchart`：用户流程、业务流程、条件分支和页面关系；
- `sequenceDiagram`：角色与产品之间的交互时序；
- `stateDiagram-v2`：页面或业务状态流转；
- `erDiagram`：仅表达会影响产品功能或业务规则的实体关系，不描述数据库表、字段、索引或存储结构。

图中的节点、条件、参与者和关系必须来自最终需求依据。使用用户和业务语言，禁止绘制函数调用、服务调用、数据库实现或其他技术流程。

### 9. 写入文档

完成全部必要澄清后，直接创建目录并写入 Markdown 文档，无需再次请求预览确认。

成功写入后，最终回复仅输出生成文件路径，不附加说明、摘要或其他文字。处于澄清阶段时，只输出当前唯一问题。

写入前检查：

- 每项需求均来自源码事实或用户明确补充、修正；
- 用户修正已正确覆盖冲突的源码现状；
- 没有推测、杜撰或 Agent 自主设计；
- 需求溯源表位于文档末尾，需求编号、源码相对路径和行号准确对应；
- 正文未内联源码路径、行号或代码标识，保持非技术化；
- 用户补充或修正未被强行映射到源码；
- 样式数值与状态均可确认；
- Mermaid 图只表达产品、交互和业务关系；
- 文件路径和功能名称符合约定；
- 未覆盖已有文件。

## 禁止内容

最终文档不得包含：

- 实现过程、实现步骤或代码逻辑；
- 函数、类、变量、组件、接口调用链等源码讲解；
- 技术选型、系统架构、算法、存储或部署方案；
- 数据库、服务、模块等技术实现细节；
- 测试方案、测试用例、测试结果或覆盖率；
- 验收标准、验收流程或验收清单；
- 开发任务、排期、工期、风险或资源计划；
- 缺乏源码事实或用户确认的推断、建议和设计。

## 失败与停止条件

遇到以下任一情况时停止写文档，并只提出当前唯一问题或说明无法继续：

- 用户未指定源码范围；
- 必要的扩读范围未获同意；
- 功能名称无法确定；
- 关键歧义尚未解决；
- 用户无法确认会改变需求含义的问题；
- 目标文件冲突但处理方式未确认。
