# Vue Component Dev

以职责边界、复用范围和稳定契约为核心，开发或审查 Vue 组件及其关联代码。

## 适用范围

适用于：

- 新增、迭代、抽离、重构和审查 Vue 业务组件、公共组件、复合组件及组件库组件；
- 约束组件相关的 hooks、composables、工具函数、类型、常量、配置、领域状态和公共 API；
- 判断代码应归属组件私有目录、项目共享层还是组件公共入口；
- 审查重复实现、职责错位、过度抽象、状态镜像、契约泄漏和行为回归。

不适用于与 Vue 组件边界无关的后端、基础设施、一次性文案修改或独立的非组件任务。

## 显式调用后的硬性约束

用户明确指定使用本 Skill 后，必须遵循以下约束：

- 必须遵循本 Skill 的文件结构、代码归属、编写要求、公开契约和验证规则；
- 不得因为改动较小、单文件实现更快或个人偏好而跳过规范；
- 不得擅自迁移 Vue 版本、Composition API/Options API、TypeScript、样式方案、测试框架或构建工具；
- 用户指定的文件、目录、组件名和公开接口应尽量保持不变；确有冲突时先指出冲突并确认，不得静默改名或迁移；
- 关键事实不明确、存在多个合理归属或会改变公开行为时，先停止并提出当前唯一必要的问题，不得猜测；
- 不得以扩大公共 API、从公共入口反向导入或增加无依据的抽象来掩盖架构问题。

## 编码前分析流程

在写入或修改代码前，按以下顺序收集事实：

1. 读取项目规则文件、目录约定、包配置、构建配置和测试配置；
2. 读取目标组件、公共入口、相邻实现、调用方和现有测试；
3. 搜索已有组件、hooks、composables、工具函数、类型、常量、配置和领域状态；
4. 优先复用已有能力，确认新增实现与已有实现的职责差异，避免重复实现；
5. 判断每段代码属于组件私有、项目共享还是公共 API，再决定文件位置；
6. 记录不能改变的现有行为：根节点、DOM 层级、attrs、class、style、事件目标与顺序、键盘行为、ARIA 语义和公开接口；
7. 只有事实足够且关键歧义已解决后，才开始修改文件。

搜索结果显示已有能力时，不得先写新实现再补充搜索。对可能共享但尚未被多个组件使用的代码，默认保留在当前组件私有范围；没有现成公共目录且确实需要共享层时，先询问用户。

## 项目兼容原则

- 以项目实际使用的 Vue 版本、Composition API 或 Options API、TypeScript 配置、样式方案、测试框架和构建工具为准；
- 沿用项目已有命名、导入、目录、导出、测试和样式模式，不建立第二套并行规范；
- 不将 Vue 响应式、模板或 DOM 依赖引入本可框架无关的领域状态；
- 不以“临时通过构建”为理由接受错误的依赖方向或不稳定的类型方案；
- 用户指定的文件、目录、组件名和公开接口优先保持稳定，任何必要变更都必须明确其影响。

## 组件目录结构

公共入口和测试位置固定遵循以下形状；只创建实际需要的文件和目录，不创建空目录：

```text
<component-dir>/
├─ index.ts                    # 公共入口
├─ src/
│  ├─ <component-name>.vue     # 组件主体
│  ├─ <component-name>.ts      # 对外组件类型
│  ├─ instance.ts              # 按需提供对外实例类型
│  ├─ service.ts               # 私有后端服务接口
│  ├─ components/              # 私有子组件
│  ├─ hooks/                   # 私有 hooks
│  ├─ composables/             # 私有 composables
│  ├─ utils/                   # 私有工具函数
│  ├─ typings/                 # 私有类型
│  ├─ constants/               # 私有常量与枚举
│  └─ config/                  # 私有配置
└─ __tests__/                  # 组件测试；测试文件统一位于 **/__tests__/**
```

具体规则：

- `<component-name>` 仅表示占位符；实际文件名必须替换为组件本身的名称，例如 `rate-limit-button.vue` 与 `rate-limit-button.ts`，不得创建通用命名的 `component.vue` 或 `component.ts`；
- `index.ts` 是唯一公共入口；不得通过私有文件路径要求调用方接入内部实现；
- `src/<component-name>.vue` 负责组件模板和组件级契约；
- `src/<component-name>.ts` 放稳定、确实需要对外暴露的组件类型；
- 只有调用方确实需要操作组件实例时，才创建 `src/instance.ts`；
- 私有后端服务接口放在 `src/service/`；
- 私有子组件放在 `src/components/`，私有 hooks 放在 `src/hooks/`，私有 composables 放在 `src/composables/`；
- 私有工具、类型、常量与枚举、配置分别放在 `src/utils/`、`src/typings/`、`src/constants/`、`src/config/`；简单组件可使用对应的单文件形式，如 `typings.ts`，但不能同时创建重复层级；
- 所有测试文件放在组件目录或项目约定的 `__tests__` 目录中，匹配 `**/__tests__/**`；不得将测试散落在组件实现目录或公共入口旁；
- 项目已有统一公共目录时，项目共享代码必须沿用该目录，不得在组件目录建立第二套公共层级。

## 组件私有代码归属

代码属于当前组件私有范围，当它同时满足以下特征中的主要部分：

- 只服务当前组件或其私有子树；
- 依赖当前组件的私有状态、Props、Slots、Expose、DOM 或交互流程；
- 与当前组件的模板、命名、事件编排或领域流程紧密相关；
- 没有稳定、独立且已被证实的跨组件复用价值。

此类代码放在当前组件的 `src/` 下，默认不从 `index.ts` 导出。

## 项目共享代码归属

代码只有在以下事实成立时才进入项目已有的公共层：

- 已被多个组件使用，或用户明确要求跨组件复用；
- 与当前组件名称、模板、DOM 和私有业务流程无关；
- 类型进入公共目录时，按公开范围归属：
  - types：稳定、可被构建并作为库 API 被用户 import 的类型；
  - typings：项目或组件内部类型，不从主入口导出。
- 代表项目统一能力，且应只有一个维护位置；
- 输入、输出和副作用边界稳定，能够脱离当前组件独立测试。

“未来可能复用”不是迁移到公共层的充分理由。没有现成公共目录且确实需要建立共享层时，先询问用户，不要自行创建第二套公共目录，目录名称参考组件目录结构中的目录名。

## 组件职责与拆分

组件主体负责：

- 模板、稳定根节点和视觉结构的组合；
- Props、Emits、Slots、Expose 以及必要的 attrs 契约；
- 直接服务组件契约的响应式状态；
- 私有子组件组合和业务级事件编排。

组件主体不应同时堆叠结构、领域状态、业务规则、复杂交互、视觉细节和通用工具逻辑。

复杂组件可以按实际耦合拆分为容器、交互结构、视觉表现、领域状态和私有子模块。拆分目标是降低耦合和维护成本，不是单纯增加文件数量；简单组件不机械拆分。

抽离或重构后必须保持既有根节点、DOM 层级、attrs、class、style、事件触发目标、事件顺序、键盘行为和无障碍语义不变，除非用户明确要求变更。

## 函数与 hooks 编写要求

- 按实际职责命名，不强行绑定组件名称；
- 判空、转换、格式化、归一化和通用校验等与模板无关的逻辑，不放在 `.vue` 文件中；
- 优先通过参数和返回值协作，减少隐式依赖、共享可变状态和不必要副作用；
- 只有依赖当前组件私有状态或 DOM 的逻辑，才保留在组件内部或当前组件的私有 hooks/composables 中；
- 依赖组件私有状态但不依赖 DOM 的响应式编排优先放入 `composables/`；依赖 DOM 生命周期、模板引用或交互事件的逻辑放入 `hooks/`；具体区分服从项目既有约定；
- 新增相近能力前必须搜索已有实现，并在实现中保持单一职责、明确差异和正确归属；
- 公共工具不反向依赖具体组件、模板、DOM 或父组件私有状态；
- 不用大型“通用工具”或万能 hook 收纳无关逻辑。

## 变量、常量、类型与领域状态

- 名称表达业务含义或实际职责，不绑定偶然使用它的组件；
- 组件私有常量放在组件目录，跨组件常量放在项目公共层；
- 稳定且对外暴露的类型放在 `src/<component-name>.ts` 或项目约定的公共类型文件；内部类型放在 `src/typings/` 或 `typings.ts`；
- Props、Emits、Slots 和 Expose 类型只有属于公开契约时才导出；内部辅助类型默认不导出；
- 领域状态尽量保持框架无关、可测试、可适配，不依赖 Vue、模板或 DOM；
- 领域状态保持唯一来源，避免多个可以独立变化的镜像 `ref`；组件只维护必要的响应式适配状态；
- 状态转换、领域校验、快照、重置和无效输入回退应具有明确的原子操作边界，不要求调用方记住隐式顺序；
- 不为假想复用强行创建类、服务层或复杂抽象。

## 公共 API 与入口导出

公共入口只导出稳定、最小、经过测试且确实需要被调用方使用的内容。以下内容默认不导出：

- 私有子组件；
- 临时方法和内部编排步骤；
- 领域规则实现和私有状态；
- 辅助类型、内部常量和私有配置。

组件实例类型按需定义在 `src/instance.ts`，并由公共入口重新导出。实例类型直接引用组件类型，例如：

```ts
import type Button from './button.vue'

export type ButtonInstance = InstanceType<typeof Button>
```

公共入口应保持依赖方向：`index.ts → src/instance.ts → src/<component-name>.vue`，不得让组件主体反向导入公共入口。

若入口需要转出目标文件的全部导出，使用 `export * from '...'`；若转出的内容全部为类型，使用 `export type * from '...'`。需要导入目标文件的全部运行时导出时，使用 `import * as Namespace from '...'`；仅导入类型时，使用 `import type * as Namespace from '...'`。只有确有命名空间需求时才使用星号导入，不得用它掩盖公共 API 设计问题；需要选择性公开或导入时，显式列出内容并保留最小契约。

## 公共契约

Props、Emits、Slots、Expose 和 attrs 组成最小且稳定的契约：

- 对外暴露面向用户任务的方法，不暴露仅供内部编排的步骤；
- 领域操作保持原子性，调用方不需要记住隐式调用顺序；
- 事件 payload 是否创建独立快照按需求、可变性和现有契约决定；只有存在外部修改风险、异步保存需求或既有隔离契约时，才要求快照隔离；
- 初始化参数必须明确是否响应式，避免调用方误解后续变更行为；
- 使用 `inheritAttrs: false` 和 `useAttrs()` 时，必须显式绑定 attrs 到约定根节点并验证属性归属；
- 不通过扩大 Props、Emits、Slots 或 Expose 来绕过职责拆分。

## 行为与无障碍兼容

抽离、重构、替换子组件或调整入口时，不得无意改变：

- DOM 层级和稳定根节点；
- `class`、`style` 和 attrs 透传归属；
- 事件触发目标、事件顺序和 payload 形状；
- 键盘行为、焦点移动和默认行为阻止；
- ARIA 角色、标签、状态和关联关系；
- 插槽渲染位置、默认内容和作用域；
- 与调用方约定的公开方法和响应式初始化行为。

子组件样式使用自己的命名空间，不依赖父组件私有 DOM 类名。组件行为发生变化时，必须在变更说明和测试中明确，而不是以“抽离”为由默认接受回归。

## 注释与源码保护

- 简单、自解释代码不添加机械注释；
- 注释除函数内使用单行注释用于解析代码逻辑外，其他地方使用/** */；
- 复杂逻辑、领域约束、兼容处理、异常回退和非直观行为说明原因，而不是重复代码字面含义；
- 重构默认保留已有有效注释，只有注释与新行为冲突时才最小化修改；
- 不得使用批量脚本删除或重写已有注释；
- 发现乱码时先验证文件编码和原始字节，不得把终端显示乱码误判为源码损坏并删除内容；
- 注释修改必须纳入 diff 审查；
- 不修改与当前组件任务无关的文件或生成物。

## 测试要求

新增、抽离或重构组件时，优先补充或更新测试，再实现代码。测试文件统一位于 `**/__tests__/**`，并按项目实际测试框架编写。

至少覆盖：

- 正常输入、边界输入、无效输入；
- Props、Emits、Slots、Expose 和公共入口；
- 根节点渲染、attrs 透传、class/style 归属和无障碍语义；
- 关键交互、键盘行为、事件目标和事件顺序；
- 若需求或现有契约要求 payload 隔离，测试调用方修改 payload 不影响内部状态；
- 领域规则、状态转换、重置和无效输入回退；
- 初始化参数是否响应式及其变更行为；
- 抽离或重构前后的 DOM、属性、事件、样式和无障碍行为一致性；
- 公共 API 只暴露约定内容，内部模块不能被误用为公开入口。

测试不是为了凑覆盖率。若项目已配置覆盖率检查，按项目阈值执行；若未配置，不擅自引入新的测试体系或依赖。

## 验证命令

按项目实际情况执行存在的命令，至少检查：

```text
lint
stylelint
unit/integration/E2E tests（项目已配置时）
coverage（项目已配置时）
typecheck（项目已配置时）
build
git diff --check
git status --short
git diff --stat
```

不要机械执行项目不存在的命令；应先读取 `package.json`、构建配置和测试配置确认命令。完成变更前至少运行与当前改动相关的 lint、类型检查、测试和 build；若项目提供统一 verify 命令，优先运行它。

遇到 `.vue` 类型导入报错时：

1. 先检查 Vue 类型声明生成链路、SFC 插件和构建配置；
2. 再检查 `<component-name>.ts`、`instance.ts` 与 `<component-name>.vue` 的依赖方向；
3. 不得用公共入口反向导入、复制类型或临时声明来掩盖根因；
4. “临时构建通过”不等于架构合理，修复后仍需运行完整相关验证。

## 完成前检查

在结束前逐项确认：

- 已读取项目规则、目标组件、相邻实现和测试；
- 已搜索并复用已有能力，没有重复实现；
- 每个新增文件都有明确的组件私有、项目共享或公共 API 归属；
- 没有无依据扩大公共 API，未错误导出内部类型、临时方法或私有配置；
- 公共入口没有反向导入，入口导出方式符合最小契约；
- 组件目录只包含实际需要的文件和目录，所有测试位于 `**/__tests__/**`；
- 没有误删或批量改写注释，没有修改无关文件或生成物；
- 没有改变既有 DOM、根节点、属性、事件、样式、键盘或无障碍行为；
- 相关 lint、类型检查、测试、构建和 Git diff 检查均已完成，失败项已如实记录。
