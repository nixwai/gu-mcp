# Vue Component Dev

按职责拆分代码，按复用范围决定归属，按最小稳定契约暴露能力。

## When to use

适用于：

- 新增或迭代 Vue 业务组件、公共组件、复合组件和组件库组件；
- 从单体组件中抽离子组件、领域状态、hooks、工具、类型、常量或配置；
- 审查重复实现、过度封装、职责错位、状态镜像和公共 API 泄漏。

不适用于后端、基础设施、一次性文案修改，或不涉及组件边界的独立样式调整。

## Core principles

- 先搜索并复用已有组件、函数、hooks、类型、常量和配置，再新增实现。
- 一个文件或模块承担一种相对稳定、可解释的职责；拆分是为了降低耦合和维护成本，不是增加文件数量。
- 组件负责视图契约和编排；领域规则、通用转换、校验和状态管理由更合适的模块负责。
- 公共模块依赖稳定的输入、输出和基础类型，不反向依赖具体组件、模板、DOM 或父组件私有状态。
- 不为假想复用过早抽象，也不把领域绑定实现命名为通用组件。
- 重构默认保持既有行为、DOM、属性归属、事件语义和无障碍语义。

## 组件、函数、变量封装原则

### 组件

组件按职责拆分，不把结构、状态、业务规则、交互、视觉和工具逻辑堆在一个文件中。

组件文件通常负责：

- 模板和稳定根节点；
- Props、Emits、Slots、Expose 等公开契约；
- 直接服务组件契约的响应式状态；
- 子组件组合和业务级事件编排。

复杂组件可按需拆出：

- 容器：尺寸、布局、背景、边框和内容承载；
- 交互结构：网格、列表、单元操作和位置/索引事件；
- 视觉表现：单个视觉对象及其表现状态；
- 领域状态：规则、状态转换、快照、重置和领域校验；
- 当前组件专用的 components、hooks、utils、typings、constants、config。

简单组件不必机械拆分。抽离后必须确认根节点、DOM 层级、attrs、事件目标、事件顺序和无障碍行为没有被无意改变。

### 函数

- 按实际职责命名，不强行带上组件名称。
- 判空、数据转换、格式化、归一化、通用校验等与组件结构无关的函数，不放在组件文件中。
- 通过参数和返回值协作，减少隐式依赖和不必要副作用。
- 只依赖当前组件私有状态或 DOM 的函数，才保留在组件内部。
- 已被多个组件使用，或明确属于项目统一能力的函数，放入项目级公共 utils。
- 不重复实现已有公共函数；新增相近函数时必须明确差异和归属。

### 变量、常量和类型

- 变量名表达业务含义或实际职责，不绑定使用它的组件名称。
- 组件私有常量放在组件内部；跨组件复用的常量放在项目公共层。
- 类型按公开范围归属：
  - types：稳定、可被构建并作为库 API 被用户 import 的类型；
  - typings：项目或组件内部类型，不从主入口导出。
- Props、Emits、Slots、Expose 类型只在确实属于公开契约时导出。
- 对外组件实例类型单独放在组件目录的 `src/instance.ts`，使用 `InstanceType<typeof Component>`，直接以 `import type Component from './component.vue'` 引用组件，保持依赖方向：`index.ts → instance.ts → component.vue`。
- 领域状态应封装为相对独立、框架无关、可测试和可适配的对象或模块。

以 GoGame 为例：它独立负责棋盘状态、规则校验、状态转换、快照和重置，不依赖 Vue、模板、DOM 或 GoBoard，因此可以被其他围棋组件、非 Vue 界面、分析工具或测试程序复用。相同原则适用于表单、分页、筛选、编辑器、拖拽和流程状态。

领域对象的目标是提升适配性和复用边界，不是绑定某个组件，也不是强行创建类或复杂抽象。

## Code ownership

### Component-local

代码放在当前组件 src 下，应满足：

- 只服务当前组件或其私有子树；
- 依赖当前组件的私有状态、Props、Slots 或 DOM；
- 没有独立的跨组件复用价值。

复杂组件按需使用：

~~~text
<component>/src/
├─ components/
├─ hooks/
├─ utils/
├─ typings/
├─ constants/
├─ config/
└─ ...
~~~

简单组件可使用 constants.ts、config.ts 或 typings.ts，不创建空目录。

### Project-shared

满足以下条件之一时，迁移到项目级公共目录：

- 已被多个组件使用；
- 与当前组件名称、模板、DOM 和业务流程无关；
- 代表项目统一能力，应该只有一个维护位置；
- 未来复用是明确需求，而不是想象中的可能性。

优先使用项目已有的 components、hooks、utils、types、typings、constants 和 config，不建立第二套公共层级。

### Public API

只有稳定、最小、经过测试且确实需要被用户调用的组件、类型、函数或配置，才从公共入口导出。内部子组件、临时方法、业务规则和实现辅助类型默认不导出。

- 组件实例类型由公共入口重新导出：`export type { ComponentInstance } from './src/instance'`。

## Public contract

- Props、Emits、Slots、Expose 和 attrs 组成最小且稳定的契约，不为单一调用场景增加临时 API。
- 对外暴露面向用户任务的方法，不暴露仅供内部编排的步骤。
- 领域操作保持原子性：一次用户操作包含其必需的状态转换，不要求调用方记住隐式调用顺序。
- 领域状态尽量保持唯一来源，组件只维护必要的响应式适配状态，避免多个可独立变化的镜像 ref。
- 事件 payload 使用独立快照，调用方修改 payload 不得影响组件内部状态。
- 初始化参数必须明确是否响应式，避免调用方误解后续变更行为。
- 使用 inheritAttrs: false 和 useAttrs() 时，必须显式绑定 attrs 到约定根节点，并测试属性归属。
- 组件抽离不能无意改变 DOM 层级、根节点、class、style、事件触发目标、键盘行为、ARIA 角色、标签或状态。
- 子组件样式使用自己的命名空间，不依赖父组件私有 DOM 类名。

## Comments and source preservation

- 简单、自解释代码不添加机械注释。
- 对复杂逻辑、非直观原因、领域约束、兼容处理、异常回退和边界行为，解释为什么。
- 重构默认保留已有有效注释；只有注释与新行为冲突时才最小化修改。
- 不得使用批量脚本删除或重写已有注释。
- 终端或编辑器出现乱码时，先验证编码和原始字节，不得把乱码显示当成源码损坏并删除注释。
- 注释修改必须纳入 diff 审查。

## Verification

新增或抽离组件时，优先补充或更新测试，再实现代码。至少覆盖：

- 正常、边界和无效输入；
- Props、Emits、Slots、Expose 和公共入口；
- 根节点渲染、attrs 透传和无障碍语义；
- 关键交互、事件顺序和 payload 快照隔离；
- 领域规则、状态转换、重置和无效输入回退；
- 抽离前后行为不变。

按项目实际命令执行：

- 构建工具对 `.vue` 类型导入报错时，先定位声明生成链路和插件配置；不得把“临时构建通过”误判为更合理的架构，也不得用公共入口反向导入掩盖问题。

~~~text
lint
stylelint
unit/integration tests
coverage（如已配置）
build

git diff --check
git status --short
git diff --stat
~~~

完成前确认：没有重复实现已有能力，没有无依据扩大公共 API，没有错误导出内部类型或临时方法，没有修改无关文件或生成物，没有误删注释，也没有改变既有 DOM、属性、事件或无障碍行为。
