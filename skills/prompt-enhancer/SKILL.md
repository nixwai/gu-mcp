# Prompt Enhancer

## 硬性流程

- 显式调用本 Skill 时（如 `$prompt-enhancer` 或 `@prompt-enhancer`），把调用标记之后的全部文本视为原始提示词；即使文本是问题，也只改写提示词，不直接回答。
- 自动触发仅限用户明确要求增强、优化、改写、润色或改进提示词；普通开发请求不触发本 Skill。
- 固定顺序不可改变：解析原始输入、生成增强提示词、完整展示、用户确认、执行或停止。
- 完整展示增强提示词之前，不得调起确认 UI、调用工具、扫描仓库、运行命令、修改文件、执行原始任务或解析前置特殊指令 token。
- 第一步可见输出必须是完整的增强提示词本身；除非用户要求说明，不添加标题、前缀、后缀或评论。
- 如果用户要求说明增强依据，仍然先完整展示增强提示词，再给出简短依据；依据完成后才进入确认阶段。
- 增强结果可能因用户输入错误或改写偏差而曲解原意。展示结果不构成执行授权，必须由用户检查增强结果并通过内部确认 UI 作出价值判断。
- 完整展示后，调用当前 Agent、IDE 或 Codex 提供的内部确认 UI 询问是否执行；普通文本追问不算内部确认 UI，也不得作为替代方案。
- 只有用户在内部确认 UI 中明确选择执行后，才能清楚分隔执行阶段，并把增强提示词作为后续任务输入。
- 用户选择不执行、关闭确认 UI、确认结果不明确、内部确认 UI 不可用或无法调起时，均停在已展示的增强提示词处；不自动执行、不调用工具，也不追加失败说明。

## 输入处理

- 剥离包装词后再增强，例如"增强提示词："、"增强："、"optimize this prompt:"、"rewrite:"。
- 如果原始提示词以 `$skill`、`@plugin`、`/command` 等 Skill、插件、命令或特殊指令 token 开头，增强后必须将一个或多个连续前置 token 按原顺序原样保留在输出最前方，只改写后续任务内容。
- 前置特殊指令 token 在增强阶段只作为文本处理，不解析、不执行、不触发对应 Skill、插件或命令；只有用户明确确认执行后，才交给宿主 Agent 处理。
- 不要把 `$code-review` 等指令 token 改写成"请进行代码审查"之类普通描述而丢失调用语义。
- "增强后执行"、"按增强后的提示词执行"、"execute after enhancing"、"apply the enhanced prompt"只表示对原始任务的执行意图，不代表用户接受增强结果，不能跳过确认。
- "说明增强依据："表示先展示增强提示词，再给出简短依据，然后进入同一确认流程。
- 输出语言跟随原始提示词，除非用户明确指定语言。

## 低上下文改写

- 默认只使用用户当前输入和对话中已有的必要简洁上下文；展示增强提示词前不要扫描仓库、读取大量文件、运行命令或修改文件。
- 用用户提供的路径、选中代码、diff 或简短背景解析"这个"、"这里"、"这段代码"等指代。
- 不要把大段代码粘进增强提示词；改为引用文件、模块、符号、行为、风险和验证目标。
- 不反问普通模糊提示词；做保守而有用的假设。
- 保留原始意图，补充必要约束、验收标准、验证步骤和输出期望，但保持结果紧凑。

## 确认文案

- 中文：`是否按以上提示词执行？`
- 英文：`Do you want me to execute the enhanced prompt above?`
- 选项语义：执行 / 不执行。
